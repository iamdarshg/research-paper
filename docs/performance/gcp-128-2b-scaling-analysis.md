# GCP 128^3 / 2B Scaling Analysis

Date: 2026-08-24. Branch: codex/gcp-128-2b (PR 41 head e321299).

## Executive summary

1. 2B parameters at 128^3 fits A100-80GB in bf16, but with only 1069 unique training geometries the model will memorize within a few hundred updates. The bottleneck is data, not capacity.
2. The best balance for the current corpus is ~500M-1B total params, not 2B.
3. Spot/preemptible VMs are safe: checkpoint/resume is production-grade.
4. A100 optimizations landed on this branch: autocast bf16 and config-driven SPSA batch chunk.

## Grokking regime analysis

Corpus information content: ~1203 kbit (1069 geometries x 192-dim x ~6 bit/dim).

| Model | Effective capacity (3% eff) | Corpus ratio | Regime |
|---|---|---|---|
| ref 96^3 w=928 d=5 (~33M) | 1273 kbit | 1.0x | AT boundary |
| 128^3 w=2048 d=8 (~95M) | 11 kbit | 9x | past threshold |
| 128^3 w=6144 d=12 (~862M) | 171 Mbit | 139x | deep memorization |
| 128^3 w=8192 d=12 (~1509M) | 314 Mbit | 255x | deep memorization |

The reference model sits exactly at the grokking boundary. Any scaling candidate will trivially memorize 1069 shapes. To make a 2B model generalize, the corpus needs to reach 10k+ unique geometries.

## Interruptible VM feasibility

Checkpoint/resume machinery verified production-grade:
- atomic_save_run_state: temp -> fsync -> os.replace -> .previous fallback.
- Full state capture: model weights, optimizer, scheduler, scaler, python/numpy/torch/cuda RNG, sample_order, threshold calibration, JSONL offset + SHA256 reconciliation.
- Compatibility fingerprinting fails closed.
- --checkpoint-every-updates N controls loss window.

A100 80GB cost estimate: on-demand $144-165 for 45h; spot drops effective cost to $50-70 when available. Well within the $270 budget either way.

Recommendation: use spot when available; checkpoint every 10-25 updates. At 2B params each run-state is ~12 GB.

## A100-class optimizations landed

Already present (merged from experiment/kernel-fusion-launch): TF32 NN GEMM math, deferred solver scalar reads, GPU-side batched guard-dot reads, foreach AdamW/EMA, coordinate-decoder gradient checkpointing, Fourier-encoded coordinate grid caching, C=2 chunk-pruned topology-guard walk, per-direction q-algebra solver workspace optimization, cached BFL max_count.

Newly landed on codex/gcp-128-2b:
1. torch.autocast("cuda", dtype=torch.bfloat16) around the diffusion forward when precision=bfloat16 is set — enables A100 tensor-core bf16 matmuls.
2. _DIRECT_SOLVER_BATCH_CHUNK now config-driven via training.direct_solver_batch_chunk in config.yaml; default stays 1 for safety, should be set to 4+ on A100-class GPUs.

Still recommended before the long run:
- bitsandbytes AdamW8bit for the 2B model (saves ~12 GB optimizer state)
- Raise coordinate_chunk_size to 65536+ on A100
- Profile the CFD path at 128^3 on GPU before committing to a config

## Quality vs capacity recommendation

DO NOT train 2B at 1069 geometries. It will memorize.

Recommended sequence:
1. Expand corpus to 2500-3500 unique geometries (process AircraftVerse 1+2, add hilift).
2. Train ~500M-800M at 128^3. This gives genuine capacity increase over the reference while remaining below the grokking threshold at expanded size.
3. Evaluate held-out geometry quality against 96^3 baseline using identical seeds and evaluation protocol.
4. Only scale to 2B if step 3 shows clear improvement AND validation loss continues decreasing without overfitting signs.
